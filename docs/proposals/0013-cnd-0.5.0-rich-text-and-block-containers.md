# Proposal — CND 0.5.0: rich text, block containers, and the elements a document actually uses

## Status

Approved (core implemented). This is a redesign of the node model, not an addition. Every CND
changes shape, every content hash changes, and the SDK's models, schema,
validation, hashing, traversal, renderers, converters, declaration,
builder and reconciliation all move with it. The work ships as one
`cnd_version` bump (`"0.5.0"`) and is cut into several implementation
plans (see [Implementation](#implementation)).

## Motivation

Converting real documents, from report templates to slide decks to
technical notes, into CND and then into Markdown shows the same losses
over and over. The compiler and the converters are not the cause: the
format has no place to put what the source said.

1. **Inline formatting is gone.** Bold, italic, inline code, strikethrough,
   superscript (`10³`), subscript (`H₂O`), underline and highlight all
   collapse into plain `text`. `10³` reads as `103`.
2. **A list item is one string.** It cannot hold two paragraphs, a code
   block or an image. A nested list inherits its parent's kind, so a
   bullet list under a numbered item comes out numbered.
3. **Table cells, term definitions, quotes and footnotes are flat text.**
   A table of images with a description column cannot be expressed. A
   multi-paragraph quote or footnote is merged into one string.
4. **Links inside non-paragraph text have no clear anchor.** An edge's
   `text_span` points into "the node's rendered text". That is well
   defined for a paragraph and ambiguous for a table (which cell?), a
   figure (caption or something else?) or a term list (which term?).
5. **Common document elements have no node.** Callouts ("Note",
   "Warning"), task-list checkboxes, a code block's file name, a long
   text description of a chart or diagram, a layout grid that is not a
   data table, and the status and version an author prints on a title
   page all get flattened or dropped.

Each could be patched with one more optional field. The patches would not
compose: marks need to know which text they index, which is problem 4;
block content inside items needs a container rule, which is problems 2
and 3. This proposal fixes the model once.

### Compatibility policy before 1.0.0

The format is pre-1.0 and is not stable. **Until `cnd_version` 1.0.0, a
minor version may break anything**, and design choices are made on
merit, not on how much they preserve. Consumers already pin to a release
tag (spec §11). This proposal states the policy in §11 so it is
explicit, not inferred.

## Principles

Four rules carry the whole design. The spec states each once, and every
node type follows them.

### 1. Prose is rich text; verbatim is a string

Every slot that holds **prose** is a `RichText` object. Every slot that
holds **verbatim** content (code, math source, `raw`) or **metadata**
(`image.alt`, `code.title`, `heading_path`, `doc.title`) stays a plain
string. The test: can an author make part of it bold or put a
cross-reference in it? If so, it is prose.

### 2. Nested nodes always live in `children`

An object that contains block nodes holds them in a field named
`children`, without exception: nodes (`heading`, `figure`, `quote`,
`admonition`) and the value objects that are not nodes (`ListItem`,
`TermItem`, `Cell`, `Footnote`). A generic walker follows one field
name.

Short **labels** attached to a node (a heading's text, a caption, a
title, a term, an attribution) are `RichText`. **Bodies** are
`children`. No slot accepts both forms. A union such as
`RichText | Node[]` would let the same content be written two ways (one
paragraph, or a `RichText`), which breaks canonical hashing and makes
every consumer handle both shapes.

### 3. Open vocabularies

Several fields take a value from a list the spec defines, but must also
accept values an author or producer invents: a figure kind such as
`"theorem"`, a callout such as `"example"`. The spec calls these **open
vocabularies** and gives them one contract:

- **Known values** have a precise definition in the spec. A producer
  uses a known value whenever one fits; it does not mint `"warn"` when
  `"warning"` exists.
- **Free values** are any other string. They are not prefixed (no
  `x-`): a prefixed value has to be renamed everywhere on the day it
  becomes standard (the lesson of RFC 6648).
- **Consumers never fail on an unknown value.** Each open field defines
  its fallback: ignore the value, or render a generic form.
- **Promotion.** A free value in wide use becomes a known value in a
  minor version.

Open vocabularies in 0.5.0: `figure.kind`, `admonition.kind`,
`Mark.kind`, `table.kind`, `code.lang`, `raw.format`, `source.type`, and
the keys of `doc.extra`.

Closed enumerations stay closed where a consumer must understand the
value exactly to process the data. The node `type` discriminator is one:
an unknown node type cannot be read.

### 4. Offsets index the text they sit beside

Every `[start, end)` span (a mark or an edge's `text_span`) indexes the
`value` of the `RichText` object that holds it, in Unicode code points
(ADR 0013). There is no "rendered text of a node" to define any more.

## Proposed change

### Model overview

```ts
// Top level
Cnd         { id, cnd_version: "0.5.0", built_at, source, doc: DocMetadata,
              nodes: Node[], bibliography: BibEntry[], footnotes: Footnote[] }

DocMetadata { title, authors, date, keywords, description, lang,
              status: string | null,              // new
              version: string | null,             // new
              extra: { [key: string]: string } }  // new

// Text
RichText    { value: string, lang: string | null,
              marks: Mark[], refs: NodeRef[], cites: CiteRef[],
              footnotes: FootnoteRef[], links: LinkRef[] }
Mark        { start: int, end: int, kind: string, raw: RawSource | null }
Numbering   { value: string, name: string | null }

// Node base: id, label, state_metadata, location (the link families move to RichText)
heading     { level, numbering: Numbering | null, text: RichText, heading_path, children }
paragraph   { text: RichText }
quote       { attribution: RichText | null, children }
code        { text: string, lang: string | null, title: string | null }
math        { text: string, raw: RawSource | null, numbering: Numbering | null }
image       { path, alt }
figure      { kind: string | null, caption: RichText | null, description: RichText | null,
              numbering: Numbering | null, children, raw: RawSource | null }
admonition  { kind: string, title: RichText | null, children }   // new
list        { ordered: bool, items: ListItem[] }
terms       { items: TermItem[] }
table       { kind: "data" | "content" | null, cells: Cell[] }
layout      { cells: Cell[] }                                     // new

ListItem    { number: int | null, checked: bool | null, children }
TermItem    { term: RichText, children }

// Pools

              year, container, doi, url, fields }

```

The sections below give the reason for each change.

### `RichText` and the link families

```json
{ "type": "paragraph",
  "text": { "value": "See Figure 2: the rate rose 103 times.",
            "marks": [ { "start": 30, "end": 31, "kind": "sup" } ],
            "refs":  [ { "label": "fig-rate", "text_span": [4, 12] } ] } }
```

- `value` is the text, passed through unaltered by every producer and
  by the builder (the spans index it).
- `lang` is the language of this text. `null` inherits from the
  enclosing text, then from the enclosing node chain, then from
  `doc.lang`. It replaces `paragraph.lang` and `quote.lang`, and it now
  reaches a caption or a cell written in another language.
- The four link families (`refs`, `cites`, `footnotes`, `links`) move
  from the node base into `RichText`. An edge belongs to **the text in
  which its marker opens**. Its owning node is the nearest node that
  holds that text. `text_span` is still nullable, for a marker that
  renders no text (a `form: "none"` citation) or one that does not close
  inside the text.
- Every list field defaults to empty and **may be omitted**. A plain
  paragraph is `{"text": {"value": "…"}}`.
- The SDK gives every node an accessor that returns the edges of all
  its texts, flattened, so resolution and validation code reads one list
  per node as before.

### Marks

A mark is a standoff span with a kind:

| `kind` | Meaning | Markdown (default) |
|---|---|---|
| `strong` | strong importance, usually bold | `**…**` |
| `emph` | emphasis, usually italic | `*…*` |
| `code` | inline code | `` `…` `` |
| `strike` | struck-through text | `~~…~~` |
| `sup` | superscript | `<sup>…</sup>` |
| `sub` | subscript | `<sub>…</sub>` |
| `underline` | underline | `<u>…</u>` |
| `highlight` | highlighted text | `<mark>…</mark>` |
| `math` | inline math; `value` holds a readable linear form, `raw` the source | `$…$` |

`Mark.kind` is an open vocabulary. **Fallback for an unknown kind:
render the covered text unchanged.** Because `value` is always the plain
text, ignoring a mark never loses words.

`Mark.raw` is optional and only `math` uses it in 0.5.0:

```json
{ "value": "The speed v = d/t is constant",
  "marks": [ { "start": 10, "end": 17, "kind": "math",
               "raw": { "format": "typst", "value": "v = d/t" } } ] }
```

Rules (normative, checked by validation):

1. **Bounds.** `0 ≤ start < end ≤ len(value)`, in code points. Empty
   marks are invalid.
2. **Free overlap.** Marks of different kinds may overlap without
   nesting: bold over "abc" and italic over "cd" are valid together.
3. **Canonical form.** Two marks of the same kind never overlap or
   touch; a producer merges them. Marks are sorted by
   `(start, end, kind)`. One rich text therefore has one serialization,
   and one hash.
4. **Atomic verbatim.** A `code` or `math` mark contains no other mark
   and is not partially overlapped by any mark or edge `text_span`. Its
   content is verbatim: nothing inside it can be bold or a link.
5. Edges are independent of marks: a link may be bold, and a bold span
   may cover half a link.

Renderers must produce well-nested output. Where two marks cross, the
renderer splits one of them at the crossing point, as text editors do,
so that the output nests.

### Block-only `quote`, `code` and `math`

- **`quote`** becomes a block container: `attribution: RichText | null`
  and `children`. A multi-paragraph quote keeps its paragraphs. An inline
  quotation stays as text in the enclosing paragraph, including its
  quotation marks. `quote.text`, `quote.block` and `quote.lang` are
  removed.
- **`code`** is block-only. Inline code is a `code` mark. `code.block`
  is removed. `code.title` is new: the label an author attaches to a
  listing, typically a file name (`"main.py"`). It is a plain string
  because it is metadata, not prose.
- **`math`** is block-only. Inline math is a `math` mark that carries
  its source. `math.block` is removed. A paragraph that contains a
  formula stays one paragraph: a reader or a search index sees
  continuous text.

### Numbering

`number` and `counter_label` merge into one object, carried by
`heading`, `math` and `figure`:

```json
"numbering": { "value": "3", "name": "Figure" }
```

- `value` is the counter value **as resolved and displayed** (`"2.1.1"`,
  `"(1)"`, `"iv"`), as `number` was (spec §6, proposal 0010).
- `name` is the counter word in the document's language, as
  `counter_label` was. It is null when the document shows no word.
- `numbering` is `null` when the element is unnumbered. A word without a
  number, which the two flat fields allowed, can no longer be written.

The names are deliberately not `count` (the value is a displayed string,
not a quantity) and not `label` (in CND, `label` is a node's
cross-reference identity; `node.label` and `node.numbering.label` would
mean unrelated things on the same node).

`ListItem.number` is unchanged: it is a list ordinal, not a document
counter.

### Lists and terms hold blocks

```json
{ "type": "list", "ordered": true, "items": [
  { "number": 1, "checked": null, "children": [
      { "type": "paragraph", "text": { "value": "Prepare the build" } },
      { "type": "list", "ordered": false, "items": [ … ] } ] } ] }
```

- `ListItem` holds `children`: any block nodes. The item's text is a
  paragraph. A nested list is a real `list` node with its own `ordered`,
  so it no longer inherits its parent's kind.
- `ListItem.checked` is new. `true` or `false` marks a task-list item;
  `null` means the item is not a checkbox.
- `TermItem` holds `term: RichText` and `children` (the definition,
  formerly `description: string`). Definitions often span several
  paragraphs or contain a list.
- `tight` is removed from `list` and `terms`. It records spacing, which
  carries no meaning for a reader. The one output where it matters,
  Markdown, derives it: a list is tight unless an item holds several
  blocks.

### Tables and layouts

```ts
table  { kind: "data" | "content" | null, cells: Cell[] }
layout { cells: Cell[] }
Cell   { row, col, rowspan, colspan, is_header, children }
```

- **`Cell` holds `children`.** A cell can contain an image, a list or
  several paragraphs. A text cell holds one paragraph.
- **`table` means rows and columns carry meaning.** The cell at row
  "Pro", column "Price" is the price of the Pro plan.
- **`layout` is new: a grid used for arrangement only**, such as two
  images side by side or a block of cards. Position carries no
  relation. Keeping it out of `table` means a consumer that processes
  tables never reads a layout as data, even if it ignores every
  optional field. `layout` covers grids only; other layout primitives
  stay flattened by producers until a corpus needs them.
- **`table.kind`** says what the table is, as a fact about the
  document:
  - `"data"`: a dataset. Each row is a record of values, such as
    instrument readings.
  - `"content"`: the cells are content to read. Examples: a feature
    comparison, or a catalogue with an image beside its description.
  - `null`: the author did not say. A consumer applies its own default
    and may infer one.

  Producers never guess. The value comes from the author.
- `TableNode.kind: "table" | "grid"` and `TableNode.content_kind` are
  removed. A grid is now a `layout` node, and `content_kind` was a
  rendering hint; `kind` states the underlying fact instead. Proposal
  0002 (automatic classification of `content_kind`) is superseded: a
  classifier, if anyone writes one, belongs to the consumer.
- `table.raw` is removed. With cells holding nodes, the model captures
  the content. A table that truly cannot be converted is wrapped in a
  `figure` that carries `raw`.

### Figures

- **`figure.description: RichText | null` is new.** It is the text
  equivalent of the figure's visual content. For a chart, it states the
  values ("Bars: A 38 %, B 27 %…"). For a diagram, it states the
  structure ("The pipeline forks after deployment into staging and
  production"). The caption is the short title shown on the page; the
  description is what a reader who cannot see the visual, a language
  model or a screen reader, needs instead. Accessibility guidance
  separates the two in the same way.
- **`figure.kind`** stays, as an open vocabulary. Its definition
  narrows: it is the figure's category, independent of language. Its
  main use is author-defined categories that `children` cannot reveal,
  such as theorems, definitions, examples or algorithms. All of those
  contain paragraphs, and only `kind` tells them apart; `numbering.name`
  is localized and absent when the figure is unnumbered.
- **`figure.raw`** stays. It is the escape hatch for content the model
  cannot express yet. New producer guidance (non-normative): a figure
  whose body is a **drawing** (a diagram, a plotted chart, a canvas) is
  emitted with `raw` filled and no scattered `children`, rather than as
  stray text labels lifted out of the drawing. A dataset beside a chart
  is a second child of the same figure (a `table` with `kind: "data"`).

### Admonitions

```json
{ "type": "admonition", "kind": "warning", "title": { "value": "Careful" },
  "children": [ … ] }
```

- `kind` is an open vocabulary. The known values are those of the
  widely used Markdown alert syntax: `note`, `tip`, `important`,
  `warning`, `caution`.
- `title` is the title as displayed, in the document's language, or
  null.
- **Fallback for an unknown kind:** render as a generic callout: a
  quote block headed by the title, or by the kind when there is no
  title.

### Footnotes hold blocks

`Footnote` becomes `{id, label, children}` (formerly `text: string`). A
footnote may contain several paragraphs or a list. Footnote content
nodes are **nodes in every respect**:

- their ids join global id uniqueness, and they may carry labels that
  `refs` can target (for example an equation inside a note);
- `location` follows the all-or-nothing rule of §2.2: on a paginated
  CND, they carry the page where the note is printed;
- validation covers them like any other node.

They stay **out of the body tree**. Walking `cnd.nodes` does not visit
them, so a consumer splitting the body into passages never mixes notes
into running text. The SDK adds a full traversal that also walks the
pools.

`BibEntry.formatted` becomes `RichText | null`: a formatted reference
carries italics (a journal title) and sometimes links.

### Document metadata

```json
"doc": { "title": "Deployment guide", "status": "Approved", "version": "1.2",
         "extra": { "client": "ACME", "reference": "PRJ-042" } }
```

- `status` and `version` are new, optional and free-form. They are the
  values **as the author declares them** on the document, such as a
  title page reading "Status: Approved, Version 1.2". They have no
  relation to `cnd_version`, and they do not contradict §11: a CND still
  carries no version history of its own. These fields record what the
  author wrote, not a build lineage.
- `extra` holds any other title-page metadata as string pairs. The spec
  defines none of its keys, and consumers may use or ignore them. **An
  `extra` key must not repeat the name of a `DocMetadata` field**, or
  there would be two contradictory values (checked by validation). A key
  in wide use becomes a named field in a minor version.

## Hashing (§10)

Three rule changes, and every hash changes at this version, as at
0.4.0.

1. **Defaults are removed before hashing.** Every field equal to its
   default (`null`, `[]`, `{}`, `false` where false is the default) is
   dropped from the hashable value before NFC and JCS. Omitting an empty
   list and writing it out therefore hash the same. A future version
   that adds an optional field no longer changes existing hashes.
2. **A node's hash excludes every nested node, wherever it sits.** This
   covers `children` and also `items[].children`, `cells[].children`
   and the `children` of a `TermItem`. A list whose third item's text
   changed has not itself changed; the item's paragraph has. `numbering`
   replaces `number` and `counter_label` in the exclusion list, since it
   is resolved presentation state.
3. **The document hash pairs each node with its full position**, not
   only its depth. The position is the depth plus the slot within the
   parent, such as `cells/3/children/0`. Moving a paragraph from cell 1
   to cell 2 keeps depth and reading order but changes the content, and
   the hash must see it. Footnote content enters the document hash with
   the pools, as before.

`fixtures/hashes.json` is regenerated.

## Traversal (§8)

- The walker descends into every container: `children`,
  `items[].children`, `cells[].children` and `TermItem.children`, in
  document order.
- `NodeTraverseContext` gains the node's **slot**, its place in the
  parent: `("children", i)`, `("items", i)` (list and term items) or
  `("cells", i)`. A consumer can then treat a list or a table as one
  unit, for example when splitting a document into passages, instead of
  emitting one passage per cell paragraph.
- A full traversal also walks the `footnotes` pool, with a pool slot.

Granularity rises with this model. Every list item and every non-empty
cell spawns at least one paragraph node. On a mixed corpus of ten
documents, the node count grows by about 55 %. Walk counters
(`doc_index`, `sibling_index`) count the new nodes. Reconciliation
(ADR 0018) gets finer: an edited list item is matched and reported on
its own, where a whole list used to be marked changed.

## Validation (§9)

New invariants, added to the §9 table:

| Invariant | Where |
|---|---|
| Mark bounds, canonical order, same-kind merge | Marks |
| `code` and `math` marks are atomic | Marks |
| Every `text_span` lies inside its text's `value` | §5 |
| No `doc.extra` key repeats a `DocMetadata` field name | §3 |
| Footnote content nodes join id and label uniqueness | §2, Footnotes |

## Rendering (§7, non-normative)

All renderers and converters follow the same policy for marks: **a
renderer renders what it supports and leaves the text of anything else
unchanged.**

**Markdown** (both the converter and the text renderer used for
language models):

- Marks render per the table above. Marks without CommonMark or GFM
  syntax (`sup`, `sub`, `underline`, `highlight`) render as **inline
  HTML by default**. CommonMark allows inline HTML, most viewers display
  it, language models read it fluently, and a viewer that strips HTML
  keeps the text. A **text-only option** drops those four to plain text
  for a Markdown output with no HTML at all. `math` renders as `$…$`.
- `admonition` with a known kind renders as a GFM alert
  (`> [!WARNING]`); an unknown kind renders as a quote whose first line
  is the title in bold.
- `ListItem.checked` renders as `- [x]` or `- [ ]`.
- `code.title` renders as a line holding the title directly before the
  fence.
- `figure.description` renders as a paragraph after the figure's
  caption. Figure placeholders (proposal 0012) include it.
- `table` renders as a GFM table when every cell holds inline-renderable
  content (one paragraph, or an image). Otherwise it renders as an HTML
  table, or as linearized rows under the text-only option.
- `layout` is flattened: cell contents in reading order, row by row.
- `doc.status`, `doc.version` and `doc.extra` render wherever the
  converter renders the other document metadata.

**HTML**: marks map to `<strong>`, `<em>`, `<code>`, `<s>`, `<sup>`,
`<sub>`, `<u>`, `<mark>`; a `math` mark keeps its source in a
`<code class="math">` element. `admonition` maps to an `<aside>` with a
kind class, and `layout` maps to a CSS grid.

**Plain text** drops all marks; a `math` mark renders its `value`.

## Declaration (§12)

- **Shorthand.** Wherever a `RichText` is expected, a declaration (and
  the Python builder) accepts a plain string, which builds
  `{"value": "<string>"}` with no marks and no edges. The full object
  form stays available to producers that compute offsets.
- An inline markup syntax, for example `markup: "See @fig-rate, it is
  **important**"` parsed into value, marks and edges, would be the
  practical answer for hand authors and language models. It is **out of
  scope** and gets its own proposal: the syntax, escaping and link
  notation need a design of their own.
- The declaration drops `number` and `counter_label` in favour of an
  authored `numbering.name`. The value stays derived by the builder.
- `links` in declarations remains out of scope (ADR 0024).

## Versioning (§11)

- `cnd_version` becomes `"0.5.0"`; the SDK release that ships it is a
  new minor version.
- §11 states the pre-1.0 policy: no compatibility guarantee before
  1.0.0.
- No 0.4 → 0.5 upgrader is shipped. A CND 0.4 holds none of the new
  information (no marks, no admonitions, no checkboxes), so an upgrade
  would only reshape it. Producers move to 0.5 by emitting it, and
  consumers move by pinning the new tag once their producer emits it.

- **Proposals**: 0002 is superseded by this one. 0010's `counter_label`

- **Authoring package** (`cnd.typ`): the table hint is renamed from

  producer concern, delivered with the producer that emits 0.5.

## Out of scope

- Graph and canvas nodes for diagrams and charts. Until they exist,
  `figure.raw` plus `figure.description` carry those visuals.
- Layout primitives other than grids (stacks, columns, absolute
  placement).
- Inline language switches inside a text (a foreign phrase in a
  sentence). `RichText.lang` covers whole texts.
- An inline markup syntax for declarations (see above).
- Richer `doc.extra` values (dates, lists): add a named field instead.

## Alternatives considered

- **Additive 0.5.0** (keep `text: string`, add `marks` beside it, add
  `children_ordered` to `ListItem`). This is cheaper to migrate, but it
  leaves problems 2–4 standing and needs a locator for every
  multi-text node. Rejected under the pre-1.0 policy.
- **`content: RichText | Node[]` for every slot.** This gives two
  encodings for one content; see principle 2.
- **Marks and edges kept on the node with a slot locator**
  (`"in": "cells[3]"`). These are path strings every consumer must
  parse, and they break when the structure moves.
- **A canonical "rendered text" per node**, with every offset into it.
  Any change to the rendering rule shifts every span. This was the
  implicit 0.4 model.
- **`body` instead of `children`**, following Typst. In Typst, `body`
  is sometimes inline content (a heading's title, a strong span), so
  the term would mislead. `children` is the term of the common JSON
  document trees and of the DOM.
- **A closed mark list limited to Markdown's own syntax.** Superscript,
  subscript, underline and highlight are too common in real documents
  to lose, and a renderer that cannot show them still keeps their text.

## Implementation

One proposal, several plans, in this order:

1. **Core**: models, generated schemas, validation, hashing, traversal
   and accessors.
2. **Renderers and converters**: plain text, Markdown (with the
   text-only option) and HTML.
3. **Declaration, builder and reconciliation.**
4. **Fixtures and goldens**: every fixture rewritten to 0.5,
