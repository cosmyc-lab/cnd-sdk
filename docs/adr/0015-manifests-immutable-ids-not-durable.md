# ADR 0015 — Manifests are immutable build artifacts; node ids are not durable

## Status
Proposed.

## Context
A CND manifest is the output of building a source document. Nothing in the
format identifies a *document* across successive builds, and the node `id`
field is described by the specification (§4) as a "Stable node identifier".
That description does not hold and cannot be made to hold cheaply:

- Producers assign node ids at build time. The reference Typst producer, the
  only one in service, mints a fresh random UUID for every node on every
  build, so recompiling a byte-identical source yields a manifest whose node
  ids match none of the previous run's. Ids are unique, not stable.
- Making them reproducible (deriving an id from a node's structural path)
  buys little: such an id survives a content edit but not an insertion or a
  reordering — the most common edits — because inserting one node shifts the
  structural path of every node after it.
- True stability across arbitrary edits is not a property a serialisation can
  carry. It is a property of a *process*. A stateless, per-build artifact has
  nothing to be stable against. The two known ways to get durable element
  identity both refuse to rebuild: either the document is mutated in place and
  identity is assigned once at insertion (CRDT/OT), or it is rebuilt and old
  and new are matched heuristically after the fact (the content-addressed
  model, where identity *is* content and editing therefore breaks it).

Consumers nonetheless need to answer two distinct questions — "did this node
change?" and "is this the same node as before?" — and today the misleading
"stable identifier" wording invites them to answer both with the id, which is
wrong for the second.

This decision fixes what CND guarantees about identity, so that the field and
its consumers can be designed against the truth rather than against the
current wording.

## Decision
**A CND manifest is an immutable build artifact.** CND does not model
in-place editing, document identity across builds, or revisions. A consumer
that needs version history keeps the manifests it considers to be versions;
the format carries no document-identity field and no revision field. This is
ADR 0006 scope discipline applied to identity: the repository defines the
representation of one built document, not the lifecycle of a document across
edits.

Consequently:

1. **Node ids are unique within a manifest, not durable across builds.** The
   specification's "Stable node identifier" wording (§4) is corrected to say
   so plainly. Uniqueness across nodes and pool entries (§2) is unchanged.

2. **The only exact, durable identity is a `label`.** A label is written in
   the *source* and the source is what survives a rebuild, so a labelled node
   can be recognised across builds and edits by name. This is the whole
   difference between naming a node and giving it an id: not the nature of the
   identifier, but where it lives. An id minted at build time exists only in
   the output and is regenerated by construction.

3. **Reproducible (deterministic) ids are rejected**, for the reasons in
   Context: they answer a question that derived content hashes already answer
   without needing ids to coincide, and wanting a regenerated artifact to be
   the same artifact contradicts immutability. If stable ids are wanted, keep
   the artifact rather than rebuild it.

## Consequences
- The two questions separate cleanly and each gets the right tool: **"did it
  change?"** is answered by derived content hashes (recorded separately), and
  **"is it the same node?"** is answered exactly by labels where the author
  supplied them, and best-effort by a reconciliation/diff facility elsewhere.
  The SDK will provide that facility (a `diff` between two manifests and an
  id-inheriting rebuild) so consumers can build their own versioning on top;
  it is specified on its own and is explicitly best-effort for unlabelled
  nodes — it cannot be otherwise, since matching across edits is the diff
  problem.
- The correction is deliberately loud. Consumers that index or annotate will
  key on node ids regardless of what the prose says, so the specification must
  state in §4 — not merely imply — that an id is not a cross-build handle, and
  point them at labels and the diff facility instead.
- "No document-identity field" has to be reconciled with `doc` metadata, which
  does identify the *work* (title, authors). The wording becomes: CND carries
  no *stable* document identity or revision. `doc` describes the work and
  guarantees nothing durable about it across builds.
- This decision changes what the `id` field promises without changing its
  shape or the schema; the accompanying spec-text edit rides in the 0.3.0
  wave. It also reframes ADR 0002's "stable" language for cross-references,
  which a separate ADR revisits when links move to label-based resolution.
- If CND ever needs in-place editing or first-class versioning — for instance
  to support an editing tool rather than a compiler — that is a change to what
  CND *is*, and must be decided by a superseding ADR, not slipped in as a
  field. This ADR deliberately closes that door for now.
